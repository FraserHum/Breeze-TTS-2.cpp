# Independent research partner: unexplored optimization surfaces

Research date: 2026-09-15. This note records an exchange with the main investigator, not new benchmark results. Local baseline is the approved calibrated Q3 depth FFNs and Calliope, with retained graph/read synchronization at approximately 0.863 wall RTF. The target remains 0.8. No runtime, model, pod, production, or GPU workload was changed in this research pass.

## What changed during the discussion

The initial instinct to try F16 output heads was challenged by the main investigator: that experiment already exists in the repository. It is a possible current-baseline replication, not an unexplored area. The official implementation also deliberately keeps its head in F32 for stability; that does not override our local result, but argues against assuming head precision is free.

I initially proposed generic residual/normalization fusion. Inspection and the main investigator's challenge showed those native fusion families already exist. The distinct remaining idea is a packed gate/up projection with a SwiGLU epilogue, not simply enabling another generic fusion flag.

Both investigators independently proposed recorded Vulkan command reuse. Static ggml graphs do not imply static Vulkan command buffers. We also agreed that host staging and sampling are too small to explain the remaining gap, and that the 43 ms depth compute phase cannot be interpreted as CPU recording cost.

I initially favored cached convolutional tail state over mixed IQ2. The main investigator identified an exactness hazard: old transformer outputs can change when the decoding window changes, so caching their downstream convolution intermediates is not automatically correct. A smaller proven receptive-field history is the simpler first experiment; state reuse requires overlap equality evidence.

### Why wave32 is a concrete, untested lever

In the pinned Vulkan source, `subgroup_size` for matvec is `device->subgroup_size` except for an Intel-specific case. `force_subgroup_size16` is derived from it, and the Q3 floating matvec pipeline receives that explicit size. With the recorded 780M device subgroup size of 64, the Q3 pipeline requests 64. The main investigator independently checked live RADV PHOENIX properties: subgroup size 64, supported minimum 32/maximum 64, and subgroup size control enabled; Mesa was 26.0.8-1ubuntu0.3. Compiled ISA still needs verification. Its subgroup workgroup size also follows this value. The RDNA1/RDNA2 default configuration table does not override an explicit pipeline argument, so simply adding RDNA3 to that table would miss this path. See [matvec pipeline creation](../../third_party/ggml/src/ggml-vulkan/ggml-vulkan.cpp).

AMD explains that RDNA's native execution is wave32 and that wave64 has different resource requirements. That is motivation to inspect actual resource use, not proof wave32 will win. More occupancy does not help every bottleneck. A changed reduction grouping may change logits, so audio equality must be checked and changed audio requires user approval. [AMD occupancy explanation](https://gpuopen.com/learn/occupancy-explained/), [RDNA performance guidance](https://gpuopen.com/learn/rdna-performance-guide/).

### Measurement discipline before another kernel

Current online Mesa documentation describes `MESA_VK_TRACE=rgp` and `MESA_VK_TRACE_PER_SUBMIT` for compute-only captures. Support for these exact options in the installed 26.0.8 build remains unverified; `perf` and `rgp` were not on the dev pod PATH. This offers a native route to examine submissions rather than inferring memory behavior from logical weight bytes divided by elapsed time. Confirm support in the installed Mesa and available analysis tools before relying on it. Current Mesa documentation says RADV profiling can select a different power state, with `RADV_PROFILE_PSTATE=peak` as the default. Verify the installed 26.0.8 behavior before capture; the current online documentation is not a version-specific guarantee. Profile durations therefore cannot replace ordinary end-to-end A/B timing, and this pass does not authorize node-wide power changes. [Mesa tracing variables and profiling state](https://docs.mesa3d.org/envvars.html).

Timebox this inspection. Missing RGP/counter tooling should not postpone a Q3-only paired FFN experiment or receptive-field trim indefinitely. A controlled intervention can establish whether a change improves elapsed time without establishing why. Use the existing packed n=1/n=2 FFN benchmark in alternating control/candidate order; promote a stable improvement to ordinary and tagged Calliope checks. Without counters, do not attribute a gain to occupancy or DRAM bandwidth, and do not generalize a null result beyond tested shapes. The history trim has an independent boundary-correctness test and needs no profiler. Recorded-command reuse, with its greater lifetime complexity, should still require evidence of material recording cost or exposed queue gaps.

For command replay, Khronos documents reusable command buffers and the execution/lifetime constraints. A replay implementation must keep descriptor sets, referenced buffers, offsets, scratch allocations, and barriers valid; it cannot reset the pool while the buffers remain in use. Per-step replay preserves the 15 host sampling decisions, whereas a single full-loop replay needs an on-device sampler. These are different changes and should not be bundled. [Khronos command buffer sample](https://docs.vulkan.org/samples/latest/samples/performance/command_buffer_usage/README.html), [command buffer specification](https://docs.vulkan.org/spec/latest/chapters/cmdbuffers.html).

The official Breeze source provides useful architectural precedent: it compiles depth layers, uses StaticCache, keeps sampling parameters in tensor buffers, captures the full autoregressive depth loop, and replays it for supported CFG shapes. It also casts the codebook head to F32. This is CUDA/PyTorch with a GPU sampler; its published H100 throughput is not a prediction for Vulkan on 780M. We should transfer the fixed-execution idea, not its reported speedup. Source inspected at commit `008f769016b0a24711becd7a4925030bc93f608c`: [official depth graph implementation](https://github.com/breezeblue-ai/breeze-tts/blob/008f769016b0a24711becd7a4925030bc93f608c/models/cudagraph/depth_decoder_graph.py).

The main investigator also evaluated the existing receptive-field recurrence against the approved model: 19,928 waveform samples imply 11 latent history frames, while the implementation retains 16. This makes five fewer conservative history frames a concrete low-effort probe. It is not a measured saving: full transformer work remains, and the retained-history boundary must be checked after the sliding window moves, including chunk sizes 1, 4 and 40.

## Lower-priority candidates and reasons

- **Packed gate/up matvec plus SwiGLU epilogue:** distinct from existing SiLU/multiply fusion. The gate and up rows are separated in the packed layout, so corresponding reductions must meet before the activation. That may require a new row layout or cross-group communication and can damage occupancy. Measure removable activation/dispatch cost before building a custom shader. Existing residual matvec/add and norm/multiply fusions are not new opportunities. [Local Vulkan fusion implementation](../../third_party/ggml/src/ggml-vulkan/ggml-vulkan.cpp), [shared packed FFN](../../src/common.cpp).
- **Selective layer/codebook compute:** the failed two-layer depth model does not logically exclude a modest codebook-dependent tail skip or a trained early exit. However, residual codebooks feed the next backbone frame; treating later codes as disposable acoustic detail is unproven. Existing student handoffs already cover this family. A small reconstruction/teacher-forced sensitivity screen is cheaper than training, but free-running delivery quality still decides acceptance. LayerSkip's primary paper uses explicit training losses and layer dropout; it is not evidence arbitrary early exit works on this checkpoint. [LayerSkip](https://arxiv.org/abs/2404.16710), [existing student handoff](../handoffs/breeze-investigations/03-parallel-depth-student.md).
- **Mixed Q3/IQ2 layers:** new configuration, old quantization family. Full IQ2 saved only a few percent and failed the user's laugh direction. Selecting layers to fix that single prompt risks overfitting. It should follow broader sensitivity and delivery fixtures, not displace the runtime investigations above.
- **Speculative depth verification:** potentially attacks sequential weight rereads, but needs a compatible draft, codebook-specific embedding/head handling, batched verification, rejection correction and cache rollback. The speech SSD paper tested CosyVoice 2 on A100, not Breeze RVQ depth. Its reported 1.4× LM improvement uses a relaxed acceptance tolerance; its zero-tolerance control was 0.509 LM-RTF against a 0.504 baseline, while the faster setting increased WER from 3.67 to 5.70. This is evidence against treating speculative speech decoding as a ready lossless speedup. [Speech SSD paper](https://arxiv.org/html/2505.15380v1).

## Why the earlier searches missed things

The gap was partly between abstraction levels. Reading about static graphs can prematurely close the question of recorded GPU commands. Kernel family timing can encourage bandwidth claims without hardware counters. General architecture labels such as RDNA support hide explicit per-pipeline subgroup overrides. Finally, records with an old tensor-parity gate or an old minimum-gain threshold can be mistaken for permanent negative results.

Confidence is high in the source-level novelty of per-pipeline wave size and recorded-command reuse, and in the arithmetic identifying 11 versus 16 history frames. Confidence in the size of any resulting speedup is low until measurement. Quality of selective layer budgets, altered attention arithmetic, or mixed quantization remains unknown.

The remedy is not a longer indiscriminate idea list. Each candidate needs an explicit status—already implemented, measured rejection, quality rejection, unevaluated hypothesis, or reopened under changed conditions—and an experiment that distinguishes its mechanism. None of the new candidates above has a measured speedup, and no combination is yet evidence that 0.8 RTF is reachable on all required workloads.
